# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

`@powerhousedao/service-offering` — A Powerhouse ecosystem package containing document models, editors, processors, and subgraphs for managing service offerings, subscriptions, and resource templates. Published to npm as an ESM library.

## Commands

```bash
# Development
bun run vetra --watch  # Start Vetra switchboard (MCP server on :4001, Connect Studio on :3000)
bun run generate       # Regenerate code from document model specs (ph-cli generate)

# Build
bun run build          # tsc → tailwind → copy-assets (full build)
bun run tsc            # TypeScript check only
bun run tsc:watch      # TypeScript check in watch mode
bun run tailwind       # Compile Tailwind CSS to dist/style.css

# Test
bun run test           # Run all tests (vitest)
bun run test:watch     # Watch mode
npx vitest run document-models/service-offering/v1/tests/services.test.ts  # Single test file

# Lint
bun run lint           # ESLint check
bun run lint:fix       # ESLint with auto-fix
```

After any code changes: **always run `npm run tsc` then `npm run lint:fix`**.

## Architecture

### Document Models (5)

All in `document-models/`, each following the versioned folder pattern `{name}/v1/`:

| Model | ID | Domain Role |
|---|---|---|
| **ServiceOffering** | `powerhouse/service-offering` | Defines service packages with tiers, pricing, and option groups |
| **SubscriptionInstance** | `powerhouse/subscription-instance` | A customer's active subscription with selected services and metrics |
| **ResourceTemplate** | `powerhouse/resource-template` | Reusable templates for service resources (audience, categories, facets) |
| **ResourceInstance** | `powerhouse/resource-instance` | An instantiated resource from a template |
| **Facet** | `powerhouse/facet` | Configurable facets with options for categorization/filtering |

### Editors (4)

React editors in `editors/`, one per model except Facet:
- `service-offering-editor` — Most complex; has custom CSS (`editor.css`) and pricing utilities
- `subscription-instance-editor` — 10+ components for billing, metrics, service management
- `resource-template-editor` — Template info, markdown editing, facet targeting
- `resource-instance-editor` — Profile management with external GraphQL queries

### Subgraph

`subgraphs/resources-services/` — GraphQL subgraph exposing `resourceTemplates` and `serviceOfferings` queries.

### Key Patterns

**Versioned folder structure**: Each document model uses `v1/` containing:
- `gen/` — Auto-generated code (types, creators, reducer wrapper, schema). **NEVER edit.**
- `src/reducers/{module}.ts` — Hand-written reducer implementations. **Edit these.**
- `tests/` — Vitest test files
- The model spec JSON (`{name}.json`) is also generated; don't hand-edit

**Reducer pattern**: Reducers export an object with operation methods. They're wrapped with Mutative, so direct state mutation is allowed. Errors auto-import from `gen/{module}/error.js`.

**Editor pattern**: Each editor has `editor.tsx` (main component), `module.ts` (editor registration), `components/` (modular UI), and uses auto-generated hooks from the document model's `hooks.ts`.

**Exports**: `index.ts` re-exports `documentModels`, `editors`, `processorFactory`, `upgradeManifests`, and `manifest`.

## CRITICAL: MCP Tool Usage Rules

**MANDATORY**: The `reactor-mcp` MUST BE USED when handling documents or document-models for the Powerhouse/Vetra ecosystem.
If the `reactor-mcp` server is unavailable, ask the user to run `ph vetra` on a separate terminal to start the server and try to reconnect to the MCP server, DO NOT run it yourself.

### Key Requirements

- Never set document IDs manually — they're auto-generated by `createDocument`
- Minimize `addActions` calls by batching multiple actions together
- Add new document model documents to `vetra-{hash}` drive unless specified otherwise
- Always check document model schema before calling addActions
- Use MCP tools for ALL document and document-model operations

## Document Model Creation Workflow

### 1. Planning Phase

**MANDATORY**: Present your proposal to the user and ask for confirmation before implementing ANY document model.

- **ALWAYS** describe the proposed document model structure (state schema, operations, modules) before creating
- **NEVER** proceed with implementation without explicit user approval of your proposal
- Break complex models into logical modules and operations

### 2. Pre-Implementation Requirements

**MANDATORY**: Check document model schema before making any MCP tool calls.

- **ALWAYS** use `mcp__reactor-mcp__getDocumentModelSchema` with `type: "powerhouse/document-model"` first
- Review input schema requirements for operations like `ADD_MODULE`, `ADD_OPERATION`, etc.
- Ensure all required parameters (like `id` or `scope` fields) are included in action inputs

### 3. Implementation Requirements

- Document model reducers must be **pure synchronous functions**
- Reducers receive current state and operation, always returning the same result
- Values like dates/IDs must come from operation input, not generated in reducer
- Reducer code goes into SET_OPERATION_REDUCER action (no function header needed)
- Reducers are wrapped with Mutative — you can mutate the state object directly
- External imports go at the beginning of the actual reducer file in `src/`
- Ensure that the reducer code of each operation in the document model schema is applied in `document-models/<document-model-name>/src/reducers/<module-name>.ts`

## Document Editor Creation Flow

When the user requests to create or make changes on a document editor:

- Check if the document editor already exists; ask the user if it should be recreated or modified
- If new, create a new editor document on the `vetra-{hash}` drive of type `powerhouse/document-editor`
- After adding the editor document, a new editor will be generated in `editors/`
- Inspect the hooks in the editor's hooks file — they're auto-generated and useful
- Read the document model schema to know how to interact with it
- Style using Tailwind classes or a scoped `<style>` tag
- Create modular components in `components/` subdirectory
- Consider using `@powerhousedao/design-system` and `@powerhousedao/document-engineering` React components

### Editor Implementation Pattern

**CRITICAL**: Use the modern React hooks pattern from `@powerhousedao/reactor-browser`.

```typescript
import { generateId } from "document-model/core";
import { useSelectedTodoDocument } from "../hooks/useTodoDocument.js";
import { addTodo } from "../../document-models/todo/gen/creators.js";

export default function Editor() {
  const [document, dispatch] = useSelectedTodoDocument();

  function handleAddTodo(values: { title: string }) {
    if (values.title) {
      dispatch(addTodo({ id: generateId(), title: values.title }));
    }
  }
}
```

The `useSelected*Document` hook is auto-generated.

## CRITICAL: Generated Files & Modification Rules

**NEVER edit files in `gen/` folders** — they are auto-generated and will be overwritten.

### Two-Step Document Model Modification Process

For ANY document model changes, **both steps are mandatory**:

1. **Update via MCP** — Use `mcp__reactor-mcp__addActions` with `SET_OPERATION_SCHEMA`, `SET_OPERATION_REDUCER`, `SET_STATE_SCHEMA`, etc.
2. **Update `src/` files** — Manually update reducer files in `src/reducers/`. These are NOT auto-generated.

**Forgetting step 2 means the `src/` code diverges from the spec. Forgetting step 1 means future code generations revert your fixes.**

## Reducer Implementation Guidelines

### Forbidden in Reducers (Non-Deterministic)

- `crypto.randomUUID()`, `Math.random()`, `Date.now()`, `new Date()`
- External API calls, side effects, async functions

```typescript
// ❌ FORBIDDEN — non-deterministic fallbacks
id: action.input.id || crypto.randomUUID();
timestamp: action.input.timestamp || new Date();

// ✅ REQUIRED — all dynamic values from action input
id: action.input.id,
createdAt: action.input.createdAt,
```

### Handling Nullable Input Types

- `InputMaybe<T>` = `null | undefined | T` (input)
- `Maybe<T>` = `T | null` (state)

```typescript
// ✅ Coerce optional inputs to match Maybe<T>
amount: action.input.amount || null,
notes: action.input.notes || [],

// ✅ Truthy checks for conditional assignment
if (action.input.field) state.field = action.input.field;

// ✅ For booleans, use explicit null/undefined checks
if (action.input.field !== undefined && action.input.field !== null)
  state.field = action.input.field;
```

### Error Handling in Operations

**MANDATORY**: Define specific error types for each operation using `ADD_OPERATION_ERROR`:
- `code`: Uppercase snake_case (e.g., `"ENTRY_NOT_FOUND"`)
- `name`: PascalCase ending with "Error" (e.g., `"EntryNotFoundError"`)
- Must use unique error names and IDs

```typescript
// ✅ Simply reference errors — they auto-import from gen/
throw new EntryNotFoundError(`Entry not found`);

// ❌ Never use generic Error, never manually import error classes
throw new Error("Something went wrong");
import { MissingIdError } from "../../gen/module-name/error.js";
```

### Testing Reducer Errors

When a reducer throws, the operation is **still added** to the document with an `.error` string property. State is NOT mutated.

```typescript
it("should return error and not mutate state", () => {
  const document = utils.createDocument();
  const initialState = document.state.global.name;

  const updatedDocument = reducer(document, setName({ name: "invalid" }));

  // Access correct operation index (0 = first operation dispatched)
  expect(updatedDocument.operations.global[0].error).toBe("Name is not allowed");
  expect(updatedDocument.state.global.name).toBe(initialState);
});

// ❌ NEVER use .toThrow() — operations are always recorded, never thrown
```

**MANDATORY**: Global state type name MUST be `<DocumentModelName>State` (not `GlobalState`):


## Dual Reactor Architecture & Codegen

The switchboard runs **two reactors simultaneously** with separate storage:

1. **Legacy Reactor** — file-based storage (`.ph/` folder). Drives created via `ph vetra` live here.
2. **New Reactor** (`storageV2`) — PGlite/Postgres (`.ph/reactor-storage/`). Independent drives.

| Tool / Endpoint | Reactor | Notes |
|---|---|---|
| `switchboard` CLI (`docs list`, `docs mutate`) | Legacy | |
| GraphQL `/d/:drive` endpoints | Legacy | |
| MCP tools (`getDrives`, `addActions`, etc.) | **New** | Different drives/data than legacy |
| Connect Studio at `:3001/d/vetra-{hash}` | Legacy | |

**CodegenProcessor** runs on the new reactor by default (`REACTOR_STORAGE_V2=true`). Use MCP tools to manage document models for codegen to trigger.

## Working with Drives

**MANDATORY**: Check the document-drive schema before performing drive operations.

### Drive Types

1. **Vetra Drive** (`vetra-{hash}`) — Source documents (document models, editors). Used for development.
2. **Preview Drive** (`preview-{hash}`, named "Vetra Preview") — Demo/preview document instances.

### Drive Operations

Always get the drive schema first via `mcp__reactor-mcp__getDocumentModelSchema` with `type: "powerhouse/document-drive"`. Key operations:
- `ADD_FILE` — Add a document to the drive
- `ADD_FOLDER` — Create a new folder
- `DELETE_NODE` — Remove a file or folder (NOT "DELETE_FILE")
- `UPDATE_NODE` — Update node properties
- `MOVE_NODE` — Move a node to different location
