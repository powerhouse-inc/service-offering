---

## 1. Rule

**When adding a service group mid-cycle, the available add-ons come from the service offering catalog, not free-form entry.**

The subscription stores `serviceOfferingId` as a PHID reference to the source offering. The editor reads the offering to present available add-on groups with their pricing.

---

## 2. Source

Service offering defines option groups with `isAddOn: true` and standalone pricing. These are the groups available for mid-cycle addition to subscriptions created from that offering.

---

## 3. Hook Implementation

### `useServiceOfferingAddons`

**File**: [useServiceOfferingAddons.ts](editors/subscription-instance-editor/hooks/useServiceOfferingAddons.ts)

- Accepts `serviceOfferingId` (PHID) and `existingGroupNames` (already in subscription)
- Fetches the offering document via `useGetDocuments`
- Filters option groups: `isAddOn === true` AND name not in `existingGroupNames`
- Returns available add-on groups with their pricing for the modal

---

## 4. Editor UI

### Add Service Group modal

**File**: [ServicesPanel.tsx](editors/subscription-instance-editor/components/ServicesPanel.tsx)

- Modal shows radio options from the offering (not free-form input)
- Each option displays the group name and pricing
- Selecting an option populates the `addServiceGroup` action with the offering's pricing

---

## 5. Constraint

The offering must be accessible from the same Reactor. Remote offerings need to be synced as a remote drive first. This is a Reactor/Switchboard limitation, not a document model limitation.

---

## 6. Bug Fix: `serviceOfferingId` PHID vs Document UUID

### Problem

`mapOfferingToSubscription` set `serviceOfferingId: offering.id` where `offering.id` is the `PHID` field on `ServiceOfferingState` — the value set by `SET_OFFERING_ID`. This field is often `null` because `SET_OFFERING_ID` was never dispatched for the offering document.

### Root Cause

`useServiceOfferingAddons` calls `getDocuments([serviceOfferingId])` which expects **document UUIDs** (the document header ID assigned by the Reactor on creation), not PHIDs. The PHID (`offering.id`) and the document UUID are different identity systems:

- **Document UUID**: Auto-generated by the Reactor when the document is created; lives in the document header. This is what `getDocuments` resolves.
- **PHID**: An optional business-level identifier set explicitly via `SET_OFFERING_ID`; lives in the document state. May be `null` if never set.

When `serviceOfferingId` contained a `null` PHID, the hook could not fetch the offering, and add-on groups were unavailable.

### Fix

`MapOfferingOptions` now includes an optional `serviceOfferingDocumentId` field that accepts the document header UUID. The `mapOfferingToSubscription` function prefers `serviceOfferingDocumentId` over `offering.id`, falling back to the PHID only if the document UUID is not provided.

This ensures the subscription stores a resolvable reference to the source offering regardless of whether `SET_OFFERING_ID` was dispatched.
